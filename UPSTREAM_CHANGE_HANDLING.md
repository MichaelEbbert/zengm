# Upstream Change Handling

How we track and selectively pull changes from the upstream project (`zengm-games/zengm`) into this fork. This is a quick-reference summary; the authoritative task breakdown lives in `docs/db_conversion.md` under **Phase 9 — Upstream Sync Process**.

> **Research only.** This file is for evaluating and deciding on upstream commits — no merges are performed from here. Anything decided as `MERGE` gets copied to a separate merge-tracking file (not created yet — that's a future activity) before any code is actually applied. Upstream merges only happen **between seasons**, never mid-season.

## Research checklist

For each commit (or commit chain), work through these before setting a decision:

1. **File overlap** — which files does it touch; do we already have local diffs in any of them?
2. **Layer conflict** — does it touch IndexedDB infra we've replaced (→ decline/skip), or a `connectLeague.ts` `upgrade<N>()` schema step (→ needs translation to a SQLite migration)?
3. **Core sim math** — does it change completion %, yards/play, fumble/sack probability, clock management, or formation/play selection? Highest scrutiny — cross-check against the rating-priority formulas already documented in `CLAUDE.md`.
4. **Coach module overlap** — does it touch play-calling decision points that `coachDecision.ts` reimplements (4th down, run/pass ratio, 2-minute drill)?
5. **Sequencing** — is this commit part of a same-topic chain (fix-then-revert, same-day follow-up) that must be taken or declined as a unit?
6. **Retroactive impact** — if merged, does it change the correct interpretation of data already sitting in existing leagues (awards, HoF thresholds, career stats)? Does it need a backfill, or can it only apply going forward?
7. **Bug validity** — for "Fix \_\_\_" commits, does the bug it addresses actually reproduce in our current, diverged code?
8. **Test coverage** — does it add/modify tests worth porting alongside the change?
9. **Dependency coupling** — is it riding along with a larger dependency bump that's really a separate decision (Electron/better-sqlite3 ABI compatibility)?
10. **Effort vs. payoff** — for pure style/refactor commits, is the merge-conflict risk against our modified files worth the near-zero gameplay value?
11. **Full commit scope** — always check the full commit stat (`git show --stat <sha>`), not just the football-filtered hunk. A commit can span multiple sports/files where only the football piece matched our path filter; applying just the filtered hunk in isolation can break the build if it depends on a companion change elsewhere (e.g. a type change in a shared, non-football-named file).

Decision guide: `MERGE` when the change has real gameplay/bugfix value, doesn't conflict with the SQLite/coach layers (or the conflict is resolvable), and is safe to apply between seasons (with a backfill plan if it has retroactive impact). `DECLINE` otherwise — record the reason inline in the Summary column or a short note.

## Why this is manual, not `git merge`/`git pull`

This fork has diverged structurally from upstream:

- **SQLite instead of IndexedDB** — all league/meta stores were migrated to `better-sqlite3` in the Electron main process (see `docs/db_conversion.md` Phases 1-7).
- **Coach module** — deterministic play-calling logic (`src/worker/core/GameSim.football/coachDecision.ts`) replaces upstream's stock play-calling, ported in from a since-eliminated Python sidecar (Phase 8).

Because of this, a straight `git merge upstream/master` would conflict heavily and risk silently reintroducing IndexedDB code paths. Upstream commits are reviewed individually and applied, translated, or skipped as appropriate.

## Categorizing upstream commits

Every upstream commit since the last-synced SHA gets one of:

| Category               | Meaning                                                                                                               | Action                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **A — Apply directly** | Bug fix/improvement in files we haven't touched                                                                       | Cherry-pick or apply as-is                                                  |
| **B — Translate**      | New `upgrade<N>()` step in upstream `connectLeague.ts`                                                                | Write an equivalent SQLite migration in our framework                       |
| **C — Manual merge**   | Touches a file we've modified (`GameSim.football/index.ts`, `game/play.ts`, `exhibitionGame.ts`, `rolldownConfig.ts`) | Read both diffs, apply upstream's intent by hand, don't clobber our changes |
| **D — Skip**           | IndexedDB infrastructure we've replaced (`Cache.ts`, `connectLeague.ts` schema, `SafeIdb.ts`, `connectMeta.ts`)       | Ignore                                                                      |

## Workflow (repeat per sync, run in plan mode)

1. `git fetch upstream`
2. `git log --oneline <last-synced-sha>..upstream/master`
3. Categorize each new commit (A/B/C/D) — record in `docs/upstream_sync_log.md` (SHA | description | category | status)
4. Apply category A changes; run `SPORT=football node --run test` after each
5. Translate category B changes into SQLite migrations
6. Manually merge category C changes; run tests
7. Update `<last-synced-sha>` in `docs/upstream_sync_log.md` and commit
